#web
методическое руководство: Систематический аудит и выявление SQL-инъекций

1. Концептуальный обзор и природа SQL-инъекций (SQLi)

В рамках современного моделирования угроз SQL-инъекции (SQLi) остаются приоритетным  вектором атаки из-за их способности полностью обходить логику прикладного уровня. Это не просто технический дефект, а стратегическая уязвимость, позволяющая атакующему вмешиваться в запросы, которые приложение направляет к своей базе данных. Последствия успешной эксплуатации SQLi выходят далеко за пределы простого извлечения данных, угрожая самой жизнеспособности бизнеса и целостности его инфраструктуры.

Основываясь на анализе векторов воздействия, последствия SQLi классифицируются по следующим уровням критичности:

- **Компрометация конфиденциальных данных:** Несанкционированный просмотр информации, доступ к которой ограничен (данные других пользователей, финансовые отчеты, системные параметры).
- **Нарушение целостности (RW-доступ):** Модификация или безвозвратное удаление данных, что ведет к перманентным изменениям в контенте и логике работы сервиса.
- **Полная компрометация инфраструктуры:** В ряде сценариев атакующий может эскалировать атаку для захвата контроля над сервером базы данных или продвижения вглубь бэкенд-сети.
- **Отказ в обслуживании (DoS):** Инициирование деструктивных запросов, приводящих к перегрузке или падению базы данных.

Манипуляция SQL-запросами позволяет злоумышленнику трансформировать легитимные функции системы в инструменты для несанкционированных действий. Для эффективного противодействия этой угрозе аудитор обязан применять системный подход к поиску уязвимостей.

2. Комплексная методология обнаружения уязвимостей

Профессиональный аудит требует тщательной проверки каждой точки входа в приложение — любого параметра (GET/POST), заголовков или куки-файлов, которые могут быть интегрированы в SQL-запрос. Фрагментарное тестирование недопустимо, так как оставляет «слепые зоны» в архитектуре безопасности.

Для достижения максимального покрытия мы комбинируем автоматизированный поиск с глубоким ручным анализом.

|Параметр оценки|Ручное тестирование|Burp Scanner (DAST)|
|---|---|---|
|**Глубина и логика**|**Максимальная.** Позволяет выявить сложные логические ошибки и специфические условия обхода.|**Ограниченная.**Эффективен для типовых паттернов, но лишен «контекстной интуиции».|
|**Скорость покрытия**|**Низкая.** Требует значительных временных затрат на каждый вектор.|**Очень высокая.**Позволяет быстро просканировать тысячи параметров.|
|**Надежность**|**Зависит от экспертности.**Позволяет подтверждать сложные Case-by-Case уязвимости.|**Высокая.** Надежно и быстро находит большинство стандартных SQLi.|

Пять фундаментальных методов ручного тестирования:

1. **Инъекция одиночной кавычки (****'****):** Отправка спецсимвола кавычки для провокации синтаксической ошибки и последующий **анализ ответов на предмет аномалий**.
2. **Синтаксический анализ входа:** Проверка обработки **математических операций** (например, `id=2-1` вместо `id=1`) или конкатенации строк. Это позволяет подтвердить наличие инъекции, не нарушая корректность запроса.
3. **Логические условия (Boolean):** Внедрение конструкций `OR 1=1` и `OR 1=2` для **фиксации систематических различий в контенте**, возвращаемом приложением.
4. **Временные задержки (Time delays):** Использование пейлоадов, инициирующих паузу в работе БД, для **фиксации разницы во времени отклика** (критично для слепых инъекций).
5. **Внеканальные взаимодействия (OAST):** Использование нагрузок, вызывающих сетевой запрос к внешнему ресурсу аудитора. Это **метод «последней надежды»**, когда стандартные методы (Boolean/Time) блокируются WAF или троттлингом.

Эффективный аудит строится на синергии: Burp Scanner обеспечивает быструю идентификацию большинства векторов, а ручные техники применяются для подтверждения уязвимостей в нетривиальной бизнес-логике.

3. Техники ручного тестирования и анализа аномалий

Основа работы аудитора — идентификация отклонений. Любое аномальное поведение приложения в ответ на модифицированный ввод — будь то сообщение об ошибке, отсутствие элементов верстки или задержка ответа — является сигналом потенциальной SQL-инъекции.

Механика логических условий (Boolean-based)

Тестирование через `OR 1=1` и `OR 1=2` позволяет определить, влияет ли ввод пользователя на логику выборки. Если ответ приложения на заведомо истинное условие совпадает с легитимным, а на ложное — нет, наличие уязвимости считается подтвержденным.

Алгоритм верификации точки входа:

1. **Провокация:** Введите одиночную кавычку `'` в целевой параметр.
2. **Анализ аномалии:** Зафиксируйте ошибку БД или изменение структуры страницы.
3. **Восстановление (Neutralization):** Используйте последовательность комментария **--**, чтобы нейтрализовать остаток запроса. Если ошибка исчезает и приложение возвращает корректные данные, это доказывает полный контроль над структурой SQL-запроса.

Продвинутый анализ (Blind SQLi)

В условиях, когда приложение подавляет ошибки (Blind SQLi), мы используем временные задержки. Если же сервер находится за фильтрами, искажающими время отклика, применяются OAST-пейлоады. OAST является наиболее обоснованным в полностью изолированных сценариях, где прямой ответ от БД невозможен. Понимание логики обработки запроса — ключ к выявлению уязвимостей, которые пропускают стандартные инструменты.

4. Практические сценарии: Извлечение данных и обход логики

Манипуляция SQL-запросами превращает стандартные механизмы приложения в рычаги несанкционированного доступа.

Кейс 1: Извлечение скрытых данных

Рассмотрим веб-каталог с фильтрацией: `https://insecure-website.com/products?category=Gifts` Внутренний запрос:

```
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

Условие `released = 1` скрывает невыпущенные товары. Применив пейлоад `Gifts'--`, аудитор трансформирует запрос:

```
SELECT * FROM products WHERE category = 'Gifts'--' AND released = 1
```

Последовательность `--` превращает остаток строки в комментарий, отсекая проверку флага `released`. В результате отображаются все товары. Использование `Gifts' OR 1=1--` приведет к выгрузке всего содержимого таблицы `products`.

Кейс 2: Подрыв логики аутентификации

Проверка учетных данных обычно выполняется запросом:

```
SELECT * FROM users WHERE username = 'user' AND password = 'password'
```

Атакующий может подать в поле username значение `administrator'--`, оставив пароль пустым. Запрос примет вид:

```
SELECT * FROM users WHERE username = 'administrator'--' AND password = ''
```

Поскольку проверка пароля закомментирована, БД вернет запись администратора, что приведет к успешной авторизации.
