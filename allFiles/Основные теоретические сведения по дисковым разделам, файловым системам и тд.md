==🔴**Секторы, блоки и адресация диска**==

Начнём с самого низа — с физического накопителя.

Представь SSD или HDD как огромную последовательность ячеек, в которых хранятся данные. Операционной системе нужно уметь обращаться к этим данным по адресам.

Для этого используются сектора.

## **Что такое сектор?**

**Сектор** — минимальная адресуемая единица дискового пространства на уровне устройства.

Например, у диска размером 100 GiB с логическим сектором 512 байт будет примерно 209,7 миллиона адресуемых секторов.

Каждый сектор имеет свой номер — LBA.

**LBA (Logical Block Addressing)** — способ адресации секторов по порядковому номеру.

Например:

- LBA 0 — первый сектор диска;
    
- LBA 1 — второй;
    
- LBA 2 — третий;
    
- LBA 1000 — сектор с номером 1001.
    

Это похоже на нумерацию ячеек массива: чтобы обратиться к конкретной ячейке, достаточно знать её индекс.

## **Logical и physical sector size**

Здесь есть важный нюанс: логический и физический секторы могут иметь разный размер.

В модели 512e накопитель представляет системе логические секторы по 512 байт, но физически записывает данные группами по 4096 байт.

Если система хочет изменить лишь 512 байт, накопителю иногда приходится прочитать весь физический сектор, изменить нужную часть и записать его обратно. Это называется read-modify-write и может снижать производительность.

## **А что такое блок?**

Не путай сектор с блоком файловой системы.

- Сектор — единица адресации устройства.
    
- Блок файловой системы — единица организации и выделения пространства внутри файловой системы.
    

Например, ext4 может использовать блоки размером 4096 байт. Один такой блок обычно соответствует восьми логическим секторам по 512 байт.

То есть диск предоставляет адресуемое пространство, а файловая система организует его под хранение файлов и метаданных.

# ==🔴**GPT и MBR — как диск хранит информацию о разделах**==

Теперь представь, что у тебя есть диск на 100 GiB.

Ты хочешь выделить:

- 20 GiB под систему;
    
- 30 GiB под данные;
    
- оставшееся пространство под резервные копии.
    

Но как операционная система узнаёт, где начинается и заканчивается каждый раздел?

Для этого существует **таблица разделов**.

Это специальная структура данных, которая описывает разделы диска: их расположение, размер, тип и другие атрибуты.

Два основных формата — MBR и GPT.

## **MBR — Master Boot Record**

MBR — старый формат разметки дисков, появившийся ещё в эпоху BIOS.

Его ключевые особенности:

- занимает первый сектор диска;
    
- содержит загрузочный код и таблицу разделов;
    
- поддерживает максимум четыре первичных раздела;
    
- для большего числа разделов используется extended partition с логическими разделами;
    
- использует 32-битную адресацию секторов, поэтому при секторах 512 байт ограничивает адресуемый объём примерно 2 TiB.
    

Почему именно четыре раздела? Потому что в MBR под записи разделов выделено место для четырёх записей фиксированного размера.

## **GPT — GUID Partition Table**

GPT — более современный формат, обычно используемый с UEFI.

Его преимущества:

- поддерживает очень большие диски;
    
- стандартно позволяет создать до 128 разделов в типичной реализации;
    
- каждый раздел имеет уникальный GUID;
    
- хранит резервную копию заголовка и таблицы разделов в конце диска;
    
- содержит контрольные суммы CRC32 для обнаружения повреждений структур GPT.
    

Самое интересное — резервная копия.

GPT хранит:

1. Основной заголовок и таблицу разделов в начале диска.
    
2. Резервную таблицу и заголовок в конце диска.
    

Если основной заголовок повреждён, утилиты могут использовать резервную копию для восстановления.

### **Что такое Protective MBR?**

GPT-диск всё равно содержит MBR в первом секторе. Но он называется Protective MBR.

Его задача — защитить GPT-диск от старых программ, которые понимают только MBR. Такие программы увидят запись, занимающую практически весь диск, и не должны решить, что диск пустой и его можно разметить по-старому.

==🔴**Как устроена файловая система: inode, superblock, journaling**==

Допустим, ты создал раздел `/dev/sdb1` и выполнил:

```
mkfs.ext4 /dev/sdb1
```

Что произошло?

Ты не просто «поставил формат ext4». Ты создал на разделе структуры данных, с помощью которых Linux сможет хранить файлы, находить их, определять права доступа и отслеживать свободное место.

Разберём три важнейшие составляющие.

## **Inode — паспорт файла**

В Linux имя файла и сам файл — не одно и то же.

**Inode (индексный дескриптор)** — структура метаданных, описывающая файл в файловой системе.

В inode хранятся, например:

- тип объекта и права доступа;
    
- UID и GID владельца;
    
- размер файла;
    
- временные метки;
    
- количество жёстких ссылок;
    
- сведения о расположении данных файла на диске.
    

А вот имя файла в inode обычно не хранится.

Имя находится в записи каталога, которая связывает имя с номером inode.

Упрощённый пример:

```
/home/user/
├── report.txt  -> inode 12345
├── notes.txt   -> inode 12346
└── backup.txt  -> inode 12345
```

Обрати внимание: `report.txt` и `backup.txt` указывают на один inode. Это пример жёстких ссылок (hard links).

То есть два имени могут ссылаться на один и тот же файл.

Именно поэтому удаление одного имени не обязательно удаляет содержимое файла: данные остаются доступны через другую жёсткую ссылку.

Когда количество жёстких ссылок становится равным нулю и файл больше не открыт процессами, файловая система может освободить его inode и блоки данных.

**Почему это важно для администратора?**

Потому что inode — ограниченный ресурс. Иногда на диске ещё достаточно свободного места в байтах, но создать новый файл уже невозможно: закончились доступные inode.

Посмотреть ситуацию можно так:

```
df -h
df -i
```

Первая команда показывает использование пространства, вторая — использование inode.

## **Superblock — паспорт файловой системы**

Если inode описывает отдельный файл, то **superblock** содержит важную информацию обо всей файловой системе.

Например:

- общий размер файловой системы;
    
- количество блоков;
    
- размер блока;
    
- количество inode;
    
- количество свободных блоков и inode;
    
- состояние файловой системы;
    
- информацию, необходимую для её монтирования.
    

Можно представить superblock как заголовок базы данных, в котором описано устройство всей структуры.

Если superblock повреждён, файловая система может стать недоступной.

В ext4 предусмотрены резервные копии superblock. Это одна из причин, почему восстановление иногда возможно даже после повреждения основного экземпляра.

Но важный момент: резервный superblock — не резервная копия твоих файлов. Это резервная копия метаданных файловой системы.

## **3.3. Journaling — журналирование**

Вот теперь интересная часть, непосредственно связанная с надёжностью Linux-систем.

Представь ситуацию:

1. Приложение создаёт файл.
    
2. Файловая система должна обновить несколько структур метаданных.
    
3. Внезапно отключается питание.
    
4. Обновиться успела только часть структур.
    

Получается потенциально несогласованное состояние файловой системы.

Чтобы уменьшить вероятность таких проблем, некоторые файловые системы используют **журналирование (journaling)**.

Упрощённо механизм выглядит так:

1. Файловая система записывает информацию о предстоящих изменениях в журнал.
    
2. Фиксирует транзакцию.
    
3. Применяет изменения к основным структурам файловой системы.
    
4. Помечает транзакцию завершённой.
    

Если система аварийно завершилась, при следующем монтировании файловая система может проверить журнал и восстановить согласованность метаданных.

Важная оговорка: журналирование не гарантирует сохранность последних записанных данных. Оно прежде всего помогает защищать внутреннюю структуру файловой системы от повреждения при аварийном завершении.

### **Режимы журналирования ext4**

У ext4 есть несколько режимов:

|Режим|Что журналируется|
|---|---|
|`data=journal`|И метаданные, и содержимое файлов|
|`data=ordered`|Метаданные; данные записываются до фиксации соответствующих метаданных|
|`data=writeback`|Метаданные; порядок записи данных не гарантируется|

По умолчанию ext4 обычно использует `data=ordered`.

# ==🔴**UUID, LABEL, mount, fstab и диагностика**==

Предположим, у тебя есть три диска:

```
/dev/sda
/dev/sdb
/dev/sdc
```

Ты создал на `/dev/sdb` раздел `/dev/sdb1`, отформатировал его в ext4 и смонтировал в `/mnt/data`.

Всё работает. Но после перезагрузки имена устройств могут измениться.

Например, вчера раздел был `/dev/sdb1`, а сегодня система обнаружила его как `/dev/sdc1`.

Если в `/etc/fstab` ты указал `/dev/sdb1`, система может попытаться смонтировать совсем не то устройство или вообще не найти нужное.

Для решения этой проблемы существуют UUID и LABEL.

## **4.1. UUID — уникальный идентификатор**

**UUID (Universally Unique Identifier)** — идентификатор, который позволяет ссылаться на файловую систему независимо от имени блочного устройства.

Например:

```
/dev/sdb1: UUID="a1b2c3d4-..."
```

Даже если раздел переедет с `/dev/sdb1` на `/dev/sdc1`, UUID файловой системы останется прежним.

Именно поэтому UUID часто используют в `/etc/fstab`.

Посмотреть UUID можно через:

```
blkid
```

Или:

```
lsblk -f
```

Небольшой нюанс: UUID есть не только у файловых систем. Например, у GPT есть GUID диска и GUID каждого раздела. Не путай UUID файловой системы с PARTUUID раздела.

## **4.2. LABEL — человекочитаемое имя**

LABEL — это метка файловой системы.

Например:

```
UUID="a1b2c3d4-..."
LABEL="backup"
```

UUID удобен для надёжной идентификации, LABEL — для удобства человека.

Можно обратиться к файловой системе через:

```
LABEL=backup
```

Посмотреть метки можно через `lsblk -f` или `blkid`.

Важный момент: метки не обязаны быть уникальными. Если две файловые системы имеют одинаковый LABEL, это может привести к неоднозначности.

## **4.3. Что делает mount на самом деле?**

Здесь важно понять концепцию, а не только синтаксис.

Linux имеет единую иерархию каталогов, начинающуюся с `/`.

Когда ты монтируешь файловую систему, ядро подключает её к определённой точке этой иерархии.

Например:

```
/
├── home
├── etc
├── var
└── mnt
    └── data
```

Ты выполняешь монтирование файловой системы в `/mnt/data`.

Теперь обращения к `/mnt/data` будут работать с содержимым смонтированной файловой системы.
При этом сама директория `/mnt/data` не становится файловой системой. Она является точкой подключения.

И ещё один нюанс: если в `/mnt/data` до монтирования лежали файлы, они не удаляются. Они просто становятся временно невидимыми, пока поверх директории смонтирована другая файловая система.

После `umount` прежнее содержимое снова станет доступно.

## **4.4. /etc/fstab — постоянная конфигурация монтирования**

Команда `mount` позволяет подключить файловую систему вручную.

Но после перезагрузки такое монтирование обычно исчезнет.

Чтобы описать постоянные точки монтирования, используется `/etc/fstab`.

У каждой записи шесть полей:

```
<source> <mountpoint> <filesystem> <options> <dump> <pass>
```

Разберём их:

|Поле|Назначение|
|---|---|
|`source`|Устройство, UUID или LABEL|
|`mountpoint`|Точка монтирования|
|`filesystem`|Тип файловой системы|
|`options`|Параметры монтирования|
|`dump`|Устаревший параметр для утилиты dump|
|`pass`|Порядок проверки файловой системы при загрузке|

Например:

```
UUID=a1b2c3d4-... /mnt/data ext4 defaults 0 2
```

Что здесь происходит?

- Система находит ФС по UUID.
    
- Монтирует её в `/mnt/data`.
    
- Использует драйвер ext4.
    
- Применяет стандартные параметры.
    
- Не использует старый механизм dump.
    
- Проверяет файловую систему на этапе загрузки с приоритетом 2.
    

Последнее поле требует отдельного пояснения:

- `0` — не проверять через стандартный механизм fsck при загрузке;
    
- `1` — обычно корневая файловая система;
    
- `2` — остальные файловые системы, которые нужно проверять.
    

Для XFS обычно указывают `0`, поскольку традиционная проверка через fsck для неё не применяется.

## **4.5. Опции монтирования**

Поле `options` может существенно влиять на безопасность и поведение файловой системы.

Вот несколько полезных параметров:

|Опция|Назначение|
|---|---|
|`defaults`|Набор стандартных параметров|
|`ro`|Монтирование только для чтения|
|`rw`|Чтение и запись|
|`noexec`|Запрещает непосредственное выполнение файлов с этой ФС|
|`nosuid`|Игнорирует биты SUID/SGID|
|`nodev`|Не интерпретирует специальные файлы устройств|
|`nofail`|Позволяет загрузке продолжиться, если устройство отсутствует|

Обрати внимание на последние три ограничения.

Представь, что ты подключаешь внешний диск с резервными копиями. Тебе необязательно разрешать запуск исполняемых файлов с него, использование SUID-бинарников или создание устройств.

В таком сценарии `noexec`, `nosuid` и `nodev` могут быть полезны.

Но не надо механически добавлять их везде: некоторые приложения действительно нуждаются в соответствующих возможностях.

## ==🟢**4.6. Инструменты диагностики**==

Вот инструменты, которые я рекомендую не просто запомнить, а научиться использовать совместно.

| Команда     | Что показывает                                         |
| ----------- | ------------------------------------------------------ |
| `lsblk`     | Дерево блочных устройств, разделы и точки монтирования |
| `blkid`     | UUID, LABEL и типы ФС                                  |
| `findmnt`   | Текущие точки монтирования                             |
| `df -h`     | Использование дискового пространства                   |
| `df -i`     | Использование inode                                    |
| `mount`     | Текущие монтирования                                   |
| `fdisk -l`  | Информация о таблицах разделов                         |
| `parted -l` | Информация о разметке дисков                           |
| `file -s`   | Определение содержимого устройства или файла           |

И особенно важны две команды, которые ты уже встречал:

```
findmnt --verify
```

Проверяет конфигурацию `/etc/fstab`.

```
mount -a
```

Пытается смонтировать все подходящие записи из `/etc/fstab`, которые ещё не смонтированы.

Последнюю команду не стоит выполнять вслепую на рабочей системе после изменения fstab: ошибочная конфигурация может привести к проблемам с монтированием.

# ==🔴**Как всё это складывается в единую картину**==

Вот самая важная часть. Посмотри на всю цепочку:

**Физический накопитель**

HDD / SSD — хранит данные в адресуемых секторах

**Таблица разделов**

GPT / MBR — описывает расположение разделов

**Раздел**

Например, /dev/sdb1 — выделенная область диска

**Файловая система**

ext4 / XFS / Btrfs — организует файлы, inode, блоки и метаданные

**Монтирование**

mount / fstab — подключает ФС к иерархии каталогов Linux

**Доступ к файлам**

Приложения и пользователи работают с файлами через привычные пути

Вот теперь у тебя должна сложиться целостная модель:

- `parted` управляет разметкой диска.
    
- `mkfs` создаёт файловую систему.
    
- `blkid` помогает определить её идентификаторы.
    
- `mount` подключает её к дереву каталогов.
    
- `/etc/fstab` описывает постоянные монтирования.
    
- `findmnt`, `lsblk`, `df` и другие инструменты помогают диагностировать состояние.
